# 嵌入式代码规范化

参照用户的《嵌入式代码规范》与样例代码，对目标嵌入式 C 代码（.c/.h）进行规范化整理。本 skill 用于“功能测试完成 → 规范化整理 → 回归测试 → 定稿”流程中的规范化整理阶段。

## 第一步（必读）：完整读取参考资料

执行任何分析或修改之前，必须完整读取本 skill 目录下的三个参考文件，禁止凭记忆或本文件的摘要执行：

1. `references/嵌入式代码规范.md` —— **规则来源**：排版布局、注释要求、命名规范、代码使用规范。
2. `references/bsp_key.c` —— **格式基准样例**（.c 侧）。
3. `references/bsp_key.h` —— **格式基准样例**（.h 侧）。

**仲裁原则**：格式细节（分区横幅样式、函数注释格式、文件头样式、对齐方式等）以 bsp_key 样例为准；规则条目（命名前缀、常量居左、指针判空等要求）以规范文档为准。两者冲突时遵循样例的格式，并在整改报告或修改摘要中注明。

注意：样例代码是**格式基准**而非逻辑基准，不要模仿样例中的具体业务逻辑写法。

## 第二步：判定工作模式

| 模式 | 含义 | 触发表述示例 |
|------|------|--------------|
| A 全量整改 | 命名规范化 + 复杂函数结构优化 + 全套注释/排版规范 | “全量整改”“彻底规范化”“命名也要改” |
| B 仅注释整改 | 只规范/补齐注释，不动任何可执行代码 | “只改注释”“补齐注释”“不动代码” |
| C 中文注释模块 | 修饰模式，与 A/B 叠加：指定模块的描述层注释用中文 | “这个模块用中文注释” |

用户未明确指定模式时，先询问，不要擅自默认。

目标为多个文件或整个目录时：逐个文件分析，汇总为一份成果（模式 A 为一份整改报告，按文件分组列出；模式 B 为一份修改摘要）。

## 模式 A：全量整改流程

1. 完整读取三个参考文件。
2. 对照规范逐项分析目标代码：
   - 命名：`g_` 全局前缀、`p_` 指针前缀、`pf_` 函数指针前缀、见名知意、宏与枚举项全大写、typedef 以 `_t` 结尾；
   - 函数实现：是否存在过于复杂的流程（过长、嵌套过深、重复代码块）；
   - 注释：文件头、分区横幅、函数文档注释、行内变量/步骤注释；
   - 排版：4 空格缩进（1 tab = 4 spaces）、80 列宽；
   - 代码使用规范：常量居左（`NULL == x`）、局部变量必须初始化等。
3. 输出**整改报告**（模板见本文末尾），然后**停止，等待用户审核**。禁止未经审核直接修改代码。
4. 用户审核通过后，统一执行报告中第一、二、三区的改动；第四区（行为变化建议）**默认跳过**，仅当用户逐项明确点名时才执行。
5. 执行完毕，按“自检清单”逐项自检，然后输出修改摘要。

## 模式 B：仅注释整改流程

1. 完整读取三个参考文件。
2. 直接规范/补齐注释：
   - 文件头：按“文件头注释处理规则”执行（缺失则新增、陈旧则重写、相符则规范格式）；
   - 分区横幅：按样例风格补齐/统一（如 Includes、Defines、Function Declarations 等）；
   - 函数文档注释：按样例的 Doxygen 风格（`@brief`、处理步骤、`@param[in/out]`、`@return`、`@retval`）；
   - 行内注释：变量定义注释、函数内步骤编号注释。
3. 不得改动任何可执行代码，不得重排代码行，不得改动任何命名。
4. 注释语言遵循模式 C 规则（默认英文）。
5. 完成后输出修改摘要。

## 模式 C：中文注释模块（修饰模式）

- **默认全英文**：未获明确指示时，所有注释一律英文；不要根据模块现有注释的语言去猜测跟随。
- 用户明确说“该模块用中文注释”时，对该模块执行：
  - **结构层**（文件头注释块、分区横幅）：仍为英文；
  - **描述层**（变量定义注释、函数文档注释、函数内行内逻辑注释）：统一用中文。
- 同一模块的 .c 与 .h 语言保持一致；描述层内部不中英夹杂。

## 文件头注释处理规则（模式 A/B 通用，重点）

每次任务必须检查目标文件最开头的文件头注释块，按三种情形处理：

1. **文件头缺失** → 按样例格式、结合当前文件实际**新增**完整文件头。
2. **文件头陈旧**（从其他文件拷贝后未改：`@file` 与当前文件名不符、`@brief`/Processing flow 描述的是其他模块、dependencies 与实际 `#include` 不符等）→ 按当前文件实际**重写**。
3. **文件头存在且与当前文件相符** → 仅按样例规范格式。

字段规则：

| 字段 | 规则 |
|------|------|
| Copyright | 固定 `Copyright (C) <年份> JesMicro.`，年份取当前日期 |
| `@file` | 当前文件名 |
| `@par dependencies` | 按该文件实际 `#include` 逐项列出 |
| `@author` | 固定 `Jace \| Development Dept. \| JesMicro` |
| `@brief` / Processing flow | 结合模块实际功能与调用方式撰写 |
| `@version` | 已存在：版本号不擅自改，提示询问用户是否更新，日期刷新为整改当天实际日期；新增：默认 `V1.0 <当天日期>`，在完成摘要中提示用户确认 |
| `@note` | 固定 `1 tab == 4 spaces!` |

语言：文件头属结构层，**任何模式下（含中文注释模块）一律英文**。

模式 A 中，文件头的新增/重写列入整改报告第三区；版本号变更不在执行范围内，仅在报告中提示询问。

## 红线（任何模式下都不得违反）

- **不得改变程序运行行为**。获批的函数结构调整也必须保持行为等价。
- 行为变化类规范项（补 NULL 检查、补函数返回值判断等）**只提建议、不代改**，列入整改报告第四区。
- 重命名必须全工程追溯：同步更新头文件声明、源文件定义、全部调用点、extern 声明；必要时 grep 整个工程确认无遗漏。
- 保留条件编译结构（`#ifdef`/`#ifndef` 等）及其内部代码的对应关系。
- 不改动与规范化无关的代码，不“顺手”做功能修改或性能优化。
- 版本号不擅自修改（由用户定稿时管理）；可在修改摘要中提示询问用户是否需要更新。文件头中的日期可更新为当天。
- 文件头必须按“文件头注释处理规则”跟进：缺失则新增、陈旧（与当前文件不符）则重写；其中版本号不擅自修改，提示询问用户确认。

## 自检清单（修改完成后逐项执行）

1. grep 搜索所有被替换的旧标识符，确认整个工程零残留。
2. 核对每个被改名的函数/变量：头文件声明、源文件定义、所有调用点、extern 声明全部同步。
3. 检查排版：缩进为 4 空格，每行不超过 80 列。
4. 通读改动处，确认注释描述与代码实际语义一致。
5. diff 复核：除整改报告中获批的改动外，无任何其他变动。

## 整改报告模板（模式 A 专用）

按四个分区列出，每区一张表：

**一、重命名类**（审批重点）

| 序号 | 文件 | 位置 | 原名 | 建议新名 | 规范依据 |
|------|------|------|------|----------|----------|
| 1 | bsp_xxx.c | L45 | `keyState` | `key_state` | 命名规范：局部变量小写下划线 |

**二、函数逻辑调整类**（审批重点，须保证行为等价）

| 序号 | 文件 | 位置 | 原逻辑 | 建议新逻辑 | 调整理由 |
|------|------|------|--------|------------|----------|
| 1 | bsp_xxx.c | key_proc() L60-L120 | 单个函数约 60 行、4 层嵌套 | 拆分为 key_proc() + static key_filter()，嵌套降至 2 层（行为等价） | 函数实现过于复杂 |

**三、注释/排版/行为等价代码调整类**

| 序号 | 文件 | 位置 | 类别 | 现状 | 建议修改为 | 规范依据 |
|------|------|------|------|------|------------|----------|
| 1 | bsp_xxx.h | 文件头 | 注释-文件头 | 缺 Processing flow 段 | 按样例格式补齐 | 注释规范：文件头 |
| 2 | bsp_xxx.c | L72 | 行为等价代码 | `if (x == 0)` | `if (0 == x)` | 代码使用规范：常量居左 |
| 3 | bsp_xxx.c | L30 | 行为等价代码 | `uint8_t cnt;` | `uint8_t cnt = 0;` | 代码使用规范：局部变量必须初始化 |

**四、行为变化建议类**（⚠ 只提示不代改，需用户逐项明确点名才执行）

| 序号 | 文件 | 位置 | 现状 | 建议 | 风险说明 |
|------|------|------|------|------|----------|
| 1 | bsp_xxx.c | L88 | 调用 HAL_xxx() 未判断返回值 | 增加返回值判断与错误处理 | 会改变错误路径行为，修改后需重点回归测试 |

**汇总**：重命名 X 项 / 逻辑调整 X 项 / 注释排版与行为等价 X 项 / 行为变化建议 X 项；涉及文件：xxx.c、xxx.h。

报告输出后，明确告知用户：“请审核以上整改项。确认后我开始执行第一、二、三区；第四区默认不执行，需要执行请逐项指明。”
