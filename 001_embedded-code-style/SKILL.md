# 嵌入式代码规范化

依据规范和成品样例整理用户指定的嵌入式 C 模块，保持运行行为，按任务范围选择工作模式和注释语言。

## 参考资料与优先级

分析目标代码前，完整读取以下资料：

- [嵌入式代码规范](references/嵌入式代码规范.md)：排版、命名、依赖、声明和代码使用规则。
- [源文件样例](references/bsp_key.c)：文件头、包含分层、变量定义与函数实现的格式。
- [头文件样例](references/bsp_key.h)：自包含、类型定义、外部声明与接口注释的格式。

冲突时按 **用户明确要求 → 规范正文明确条款 → 样例格式** 处理，并简要说明实质冲突。规范正文优先于文档中仍沿用旧写法的示例；样例仅提供格式参考，不作为业务逻辑或规范例外的依据。

## 工作模式

| 模式 | 修改范围 |
|------|----------|
| A 全量整改 | 命名、依赖、声明、注释、排版，以及必要且确认行为等价的代码调整 |
| B 注释整改和排版 | 注释、缩进、换行、空行和对齐；保留标识符、表达式、语句顺序与依赖关系 |

根据用户指定模式或明确的任务意图选择；只有无法判断 A/B 时才询问。目标涉及多个文件时，按文件分组汇总结果。用户明确限定“只改注释”时，进一步收窄模式 B，不重排代码或调整代码行的排版。

## 注释语言

语言配置独立于工作模式，未指定时默认 **中英混合**：

| 配置 | 文件头、分区标题 | 函数、变量、逻辑及包含分层注释 |
|------|------------------|------------------------------|
| 全中文 | 中文 | 中文 |
| 全英文 | 英文 | 英文 |
| 中英混合 | 英文 | 中文 |

语言选择针对自然语言说明。保留 Core、middleware、BSP 等专业术语，以及公司名称、人名、文件名、代码标识符和 Doxygen 标签；全中文也不强行翻译这些内容。同一模块的 .c/.h 使用一致配置，用户指定的局部语言要求优先。

## 共用整理规则

### 命名与声明

- 函数采用“模块前缀 + 一个下划线 + 大驼峰功能名”。普通模块前缀用大驼峰，如 `Key_Scan`、`Bootloader_JumpToApp`；芯片型号和专业缩写保留惯用大小写，如 `AT24Cxx_ReadData`、`IIC_Init`。同一模块前缀统一，第三方和自动生成接口保留原命名。
- 宏和枚举项全大写；typedef 类型小写并以 `_t` 结尾；普通变量小写、下划线分隔。全局变量使用 `g_`，显式指针变量使用 `p_`，函数指针使用 `pf_`；不因句柄类型内部是指针就机械重命名其句柄变量。
- 文件名全小写、下划线分隔，第三方及自动生成文件可保留原名。重命名同步声明、定义、调用点、extern 和必要的工程引用。
- 共享变量在所属 .c 定义一次，在对应 .h 用 extern 声明；其他模块包含该 .h 使用。仅当前 .c 使用的全局变量采用 static；改变链接可见性前核实实际使用范围。

模式 B 发现上述问题时列为建议，不执行重命名或声明迁移。

### 头文件依赖与分层

- .h 包含自身声明依赖的头文件，不要求使用方提前包含其他文件；仅实现需要的依赖放在 .c。
- .c 首先包含自身对应的 .h；其余依赖以及 .h 的依赖按实际层级由底到顶排列，例如 C 标准库 → Core/HAL → 中间件 → 上层用户模块，不为凑齐分层引入无用依赖。
- 同层头文件连续排列，各层之间空一行，只在该层第一条 `#include` 右侧标注一次层级。层内也遵守实际先后依赖，如 FreeRTOS.h 在 queue.h 前。
- 模式 B 保留包含项及其顺序，只补分层注释、空行和对齐；包含项增删、顺序调整、依赖迁移列为模式 A 建议。

### 注释与排版

- 统一 4 空格缩进，1 Tab 等于 4 Spaces；行宽不超过 80 列，中文按显示宽度计。长参数、条件和注释适当换行。
- 采用样例的成对分区横幅；根据文件实际内容设置 Includes、Defines、Declaring、Variable Definitions、Function Definitions 等分区，文字随语言配置调整。
- 每个函数有 Doxygen 注释，说明实际功能、必要处理步骤、参数方向、返回值和适用限制。声明与实现的描述一致，不虚构错误路径、返回状态或时序。
- 变量、枚举项和关键逻辑步骤补齐有意义的说明；注释随实际实现更新，不照抄样例的按键业务。

### 文件头

文件头缺失时补齐，与当前文件不符时重写，相符时规范格式；语言按本次配置执行。

| 字段 | 要求 |
|------|------|
| 版权 | 用户模块采用 `Copyright (C) <当前年份> JesMicro.` 模板；保留第三方已有版权和许可归属 |
| 文件名 | `@file` 与当前文件名一致 |
| 依赖 | 按实际直接 `#include` 的顺序逐项列出 |
| 作者 | `Jace \| Development Dept. \| JesMicro`；中文配置可翻译部门说明，保留人名及公司名称 |
| 功能与流程 | 根据当前模块功能及调用方式撰写 |
| 版本 | 保留已有版本号；缺失时默认 `V1.0`；仅按用户明确要求变更，不自动迭代或反复询问升级 |
| 日期与注意事项 | 日期更新为整改当天；注明 1 Tab 等于 4 Spaces，文字随语言配置调整 |

### 代码使用与行为边界

- 检查局部变量初始化、常量居于相等比较左侧、指针使用前判空，以及返回值处理。只有确认行为等价的代码调整才可纳入常规整改；补初始化也须结合实际路径判断。
- 区分返回值语义：void 调用无需返回值判断；数据返回值用于业务判定；状态返回值按接口约定检查。不要给 HAL_GetTick() 等数据读取函数机械套用成功/失败判断。
- 新增判空、错误处理、超时或其他可能改变行为的修改只列为建议，除非用户明确授权对应行为变化。样例中未检查 printf()、osDelay() 返回值，不代表其他模块可忽略规范。
- 保留条件编译对应关系、运行时序和日志内容；不顺带做功能修改或性能优化。

## 模式 A 执行流程

1. 对照上述规则检查指定文件，必要时提出行为等价的函数结构调整。
2. 默认先输出整改报告并等待审核；若已有审核或明确执行授权，按授权范围直接执行，并附修改摘要，不重复请求同一授权。
3. 执行获批的常规整改；行为变化建议不随“全量整改”自动执行，仅执行用户明确授权的对应项目。
4. 简要验证并交付，注明保留问题及未执行建议。

## 模式 B 执行流程

直接完成指定范围的注释与排版整理，遵循语言配置和文件头规则。将命名、依赖、声明及行为问题列为建议，完成后输出简短修改摘要。

## 报告与交付

模式 A 报告按文件分组，分为四类；仅展开有内容的类别：

| 类别 | 记录内容 |
|------|----------|
| 重命名 | 文件、位置、原名、新名及依据 |
| 必要结构调整 | 原结构、目标结构、必要性及行为等价说明 |
| 注释、排版与行为等价调整 | 现状、拟修改内容及依据 |
| 行为变化建议 | 问题、建议、行为影响及是否已获对应授权 |

审核待定时明确本次待审范围。交付说明修改内容、验证结果和未整改项，不将保留问题描述为已完全符合规范。

## 简要自检

复核 diff、注释语言与语义、4 空格/80 列及修改范围；涉及重命名时确认引用同步且无旧标识符遗漏。接口或依赖调整执行适当编译验证，完成后简述结果即可。
